# ТЗ бэкенду: «сделка» и чат на бирже (Приделе)

Документ для Марии и Дианы. Фронт уже умеет всю логику биржи локально (офлайн-демо).
Чтобы заработал **онлайн между двумя устройствами** (заказчик и мастер — разные телефоны),
нужен сервер, который хранит проекты/отклики/сделку/чат и отдаёт их обеим сторонам.

## Как устроен фронт (важно для бэка)

Вся биржа на фронте проходит через **один слой данных** —
[`lib/services/marketplace_local_store.dart`](../lib/services/marketplace_local_store.dart).
Экраны не ходят в сеть напрямую: они зовут методы этого стора. Сейчас стор пишет в
локальную память телефона (`SharedPreferences`). Когда появятся эндпоинты ниже —
переключаем **каждый метод стора** на HTTP-вызов (с fallback на локальную копию),
и экраны менять не нужно.

Базовый префикс — `{apiBaseUrl}` = `…/api/v1` (см. `lib/config/backend_routes.dart`).
Авторизация — `Authorization: Bearer <token>` (как в существующих `/projects*`).

Статусы проекта (фронт ждёт ровно эти строки от поля `status`, маппинг уже есть в
`lib/services/project_service.dart`): `draft` · `published` · `in_work` · `closed` · `archived`.

---

## 1. Проекты заказчика

Частично **уже есть** (`project_service.dart`): `POST /projects`, `PATCH /projects/{id}/map-data`,
`GET /projects/my`. Нужно дополнить:

| Метод | Эндпоинт | Что делает | Метод фронта |
|------|----------|------------|--------------|
| POST | `/projects/{id}/publish` | Перевести `draft → published`. Тело: `{ district, address }`. Сервер кладёт заявку в ленту мастеров. | `syncPublishedProject` |
| GET  | `/projects/{id}` | Один проект со счётчиком откликов и выбранным мастером. | — |

Поля проекта, которые читает фронт: `id, title, status, updated_at, responses_count,
work_type, budget, address, spec, map_data, selected_master_id, selected_master_name`.

**Валидация публикации** (фронт уже не пускает без этого, но продублируйте на сервере):
нельзя публиковать без `work_type` и `spec`.

---

## 2. Лента заказов (мастер)

| Метод | Эндпоинт | Что делает | Метод фронта |
|------|----------|------------|--------------|
| GET | `/orders?district=&work_type=` | Список опубликованных заказов (всех заказчиков), с фильтрами по району и типу работ. | `orderFeed` |

Поля карточки: `id` (= id проекта), `work_type` (показывается как заголовок — это
**название** заказа, одинаковое для заказчика и мастера), `budget_label`, `district`,
`address_short`, `teaser`, `has_3d`, `full_spec`.

⚠️ Сейчас на фронте район берётся из адреса заказчика. На сервере фильтры района лучше
сделать **динамическими** (по реально присутствующим в ленте районам), а не фиксированными САО/ЗАО.

Закрытая сделка (`in_work`/`closed`) из ленты **исчезает**.

---

## 3. Отклики мастеров

| Метод | Эндпоинт | Что делает | Метод фронта |
|------|----------|------------|--------------|
| POST | `/projects/{id}/bids` | Мастер откликается. Тело: `{ price_offer, duration_offer, message }`. Увеличивает `responses_count` проекта. | `submitMasterBid` |
| GET  | `/projects/{id}/bids` | Все отклики по проекту (видит заказчик). | `bidsForProject` |
| GET  | `/bids/my` | «Мои отклики» мастера со статусами. | `myMasterBids` |

Поля отклика: `id, master_id, master_name, specialty, rating, completed_jobs,
price_offer, duration_offer, message, status`.
Статус отклика (`status`): `sent` · `selected` · `declined`.

`responses_count` проекта = число реальных откликов (фронт больше не доверяет
захардкоженным числам — сервер должен возвращать факт).

---

## 4. Сделка: заказчик выбирает мастера  ⭐ ядро

| Метод | Эндпоинт | Что делает | Метод фронта |
|------|----------|------------|--------------|
| POST | `/projects/{id}/select-master` | Тело: `{ bid_id }`. Транзакция (см. ниже). Возвращает созданный/найденный чат. | `selectMasterForProject` |

Что обязан сделать сервер атомарно:
1. Проект → `in_work`, проставить `selected_master_id` / `selected_master_name`.
2. Выбранный отклик → `selected`, **все остальные отклики этого проекта → `declined`**.
3. Заказ убрать из ленты мастеров.
4. Создать (или найти) **чат** заказчик ↔ выбранный мастер, привязанный к проекту.
5. Уведомить мастера (push/почта) — чтобы он узнал результат (см. отчёт тестировщика, п. #2).

Это самый важный эндпоинт: без него «главная ценность продукта» не работает ни на одной стороне.

---

## 5. Чат заказчик ↔ мастер

| Метод | Эндпоинт | Что делает | Метод фронта |
|------|----------|------------|--------------|
| POST | `/chats` | Создать/найти диалог. Тело: `{ master_id, project_id }`. Идемпотентно. | `ensureChatThread` |
| GET  | `/chats/my` | Список диалогов пользователя. | `directChats` |
| GET  | `/chats/{threadId}/messages` | История сообщений. | `messagesForThread` |
| POST | `/chats/{threadId}/messages` | Отправить сообщение. Тело: `{ text, image? }`. | `appendMessage` |

Поля диалога: `id, peer_name, master_id, project_id, project_title,
last_message_preview, updated_at`.
Поля сообщения: `id, text, mine` (или `author_id`, фронт вычислит `mine`), `at`, `image_path`.

Для realtime желателен websocket/long-poll на новые сообщения; на старте достаточно
опроса `GET …/messages` при открытии чата.

Прикрепление файлов: фронт уже отправляет картинку (`image`). Нужен upload (multipart
или presigned URL) и хранение пути в сообщении.

---

## Порядок внедрения (рекомендация)

1. **#4 select-master** + **#3 bids** — замыкают сделку. Главный приоритет.
2. **#5 чат** — диалог и сообщения.
3. **#2 лента** + **#1 publish** — синхронизация заявок между ролями.

Когда эндпоинт готов — соответствующий метод в `marketplace_local_store.dart`
переключается на него (одно место на метод), экраны не трогаем.
